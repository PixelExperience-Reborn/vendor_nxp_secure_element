# Independent PixelExperience-Reborn Android 17 — row 174: NXP Secure Element HAL boundary

**Audit date:** 2026-11-07. **Target:** independently designed PE-Reborn AOSP17; future Xiaomi POCO F5 Pro / Redmi K60, `mondrian` (SM8475). **Scope:** pinned source, interface/ownership and SE integrity review, **not** a flashable ROM or device-tested HAL.

## Outcome — use official Android17, reject archived HIDL as a source tree

Keep official `platform/hardware/nxp/secure_element` as the **one NXP SE HAL source owner** (already present in the manifest), official `platform/system/secure_element` as the OMAPI/system owner, `platform/hardware/nxp/nfc` as the NFC HAL owner and `platform/packages/modules/Nfc` as NFC Mainline. The 2023 PE fork `vendor/nxp/secure_element` exposes obsolete HIDL SE v1.2, NXP HIDL eventprocessor and `nxpese`, P73 SPI libraries, a boot-time JCOP/LS updater, and inherited product/sepolicy assumptions. **Do not import or install** the old checkout into PE-Reborn Android17.

Official Android17 `hardware/nxp/secure_element` already contains the `snxxx/` NXP SE implementation from the modern AOSP source line. NXP `nfcandroid_se_hidlimpl` branch `br_ar_17_aosp_mainline`, release 17.07.00, is useful as a **verified upstream comparison** for AIDL and current SE/OMAPI functionality, **not** a parallel HAL namespace. Its Android17 service is `android.hardware.secure_element-service.nxp`, **system SE AIDL V1** instance `ISecureElement/eSE1`, with NDK Binder. Merely having a source implementation does **not** prove mondrian's actual NFCC/eSE, UICC, firmware, SE applications or financial certification.

## Findings in the old 2023 SE HAL

1. `Android.bp` builds `ese_spi_nxp.p73`, `ls_client.p73`, `android.hardware.secure_element@1.2-service.p73`, and `vendor.nxp.eventprocessor@1.0`. The HIDL service links `android.hardware.secure_element@1.0/@1.1/@1.2`, `vendor.nxp.nxpese@1.0`, `vendor.nxp.nxpnfc@2.0` and `vendor.nxp.nxpnfclegacy@1.0`. It is **not** the new NDK AIDL V1 HAL.
2. `1.2/NxpEseService.cpp` starts HIDL `ISecureElement` using a terminal name from `EseConfig`, default **`eSE1`**, registers NXP vendor event and extension services and calls **`spiEseUpdater.checkIfEseClientUpdateReqd()`** before registration and **`spiEseUpdater.doEseUpdateIfReqd(...)`** afterwards. The eSE updater has SPI/NFC JCOP/LS paths, including `SpiEseUpdater::handleJcopOsDownload()`. This source path can change SE firmware/security state and must not be imported on conjecture.
3. Its device VINTF fragment declares HIDL SE **1.2** `ISecureElement/eSE1`, **`SIM1`** and **`SIM2`**, plus NXP `eventprocessor@1.0/default` and `nxpese@1.0/default`. The service code visible in this archive registers an instance from the SPI terminal configuration; it does **not itself prove that SIM1/SIM2 instances actually exist**. Never claim physical UICC capability because a template XML lists it. If included without correct matching services, this could fail VINTF/OMAPI tests.
4. `se-vendor-product.mk` installs `android.hardware.secure_element@1.2-service.p73`, copies `libese-nxp-P73.conf` to `vendor/etc/libese-nxp.conf`, and conditionally advertises `android.hardware.nfc.ese` and `android.hardware.se.omapi.ese` features. These declarations cannot be treated as evidence of actual SE hardware.
5. The old example `libese-nxp-P73.conf` assumes `NXP_ESE_DEV_NODE="/dev/p73"`, `NXP_POWER_SCHEME=0x02`, `NXP_SPI_INTF_RST_ENABLE=0x01`, includes old OMAPI signature lists and development debug settings. The archived `sepolicy/file_contexts` labels `/dev/p73`. **Do not copy** old power, routing, signatures, device nodes, GPIO reset, file_contexts or SE permissions into a new mondrian ROM without direct verified hardware/vendor evidence and Android17 policy review.
6. `extns/impl/NxpEse.cpp` HIDL vendor `ioctl` reads `&inOutData[0]` and can `memcpy` the native `ese_nxp_IoctlInOutData_t` size without an obvious `inOutData.size() >= sizeof(...)` guard in the wrapper. **Potential length-validation/security review item, not a confirmed exploitable bug or shipped vulnerability.** Do not re-enable arbitrary vendor IOCTL surfaces. Actual reachability depends on Binder caller policy and selected services.
7. The archive's `vendor_framework_compatibility_matrix.xml` includes **optional old vendor HIDL** interfaces and LineageOS-era headers. These are **not** the independently engineered PE-Reborn AOSP17 product's FCM, and cannot be imported to paper over VINTF problems.

## Modern SE AIDL V1: current source and nuanced dependencies

- NXP Android17 `snxxx/aidl/Android.bp`: `android.hardware.secure_element-service.nxp` is a vendor `cc_binary` with `libbinder_ndk`, `android.hardware.secure_element-V1-ndk`, `vendor.nxp.nxpnfc_aidl-V1-ndk` and SE/NFC vendor libraries. The installed VINTF fragment `snxxx/aidl/secure_element-service-nxp.xml` declares precisely `android.hardware.secure_element` AIDL V1 `ISecureElement/eSE1`.
- **Nuance:** current AIDL service still lists `android.hardware.nfc@1.2` and `android.hardware.nfc-V1-ndk` in `shared_libs`. A modern AIDL entrypoint is **not proof that all internal compatibility dependencies are gone**. Soong/ELF and device vendor binary compatibility must be checked. Do not delete compat layers based solely on file naming.
- NXP Android17 `snxxx/aidl/NxpEseService.cpp` waits for `android.hardware.nfc.INfc/default` and starts the SE native Binder service. It contains a conditional VirtualISO path, which is **not proof** mondrian has multiple physical eSE chips. Product VINTF and registered instances must agree exactly.
- A current `libese_vendor_extn/se_update_agent/Android.bp` includes a separate `se_update_agent.nxp` **`enabled: false`** and sources capable of OMAPI/script update. Its `se_update_agent.nxp.rc` has `on fs` and property-activated service triggers. **The module must remain unselected** unless a complete OEM-signed update protocol, rollback/recovery, SELinux and user-data safety model has been proven. `enabled: false` in Soong alone is not a general security guarantee if another product overrides it.
- Current `snxxx/1.2/Android.bp` keeps `android.hardware.secure_element_snxxx@1.2-service` but **`enabled: false`**. Do not equate source coexistence with active dual HAL registration.
- `frameworks/sems/Android.bp` modern `com.nxp.sems` is **`enabled: false`**, `sdk_version: "29"`. No reason to add the obsolete framework/permission module to the Android17 platform.
- The NFC HAL AIDL V2, SE HAL AIDL V1, vendor NXP AIDL V1 and OMAPI access rules are **separate interfaces**. Preserve all independent source owners and avoid legacy `INxpEse` or `INxpEseEvtProcessor` HIDL injection.

## Confirmed official SE security fix — newer AOSP17 source, isolated candidate

An actual Git diff (not only a tag comparison) was inspected in [GitHub Actions #42322285010](https://github.com/PixelExperience-Reborn/vendor_nxp_secure_element/actions/runs/42322285010), comparing immutable official AOSP17 SE `android-17.0.0_r1` (`ebc3542b...`) against `android-security-17.0.0_r3` (`8aec22fd...`). Exactly **10 paths changed, zero added and zero removed**:

- `pn8x/1.0/SecureElement.cpp`, `pn8x/1.1/SecureElement.cpp`;
- `snxxx/1.0/{SecureElement.cpp,VirtualISO.cpp}`, `snxxx/1.1/{SecureElement.cpp,VirtualISO.cpp}`, `snxxx/1.2/{SecureElement.cpp,VirtualISO.cpp}`;
- **`snxxx/aidl/SecureElement.cpp`** and **`snxxx/aidl/VirtualISO.cpp`**.

**Verified AIDL correction:** in `openLogicalChannel()`, official security-r3 checks `rspApdu.p_data[0] < mMaxChannelCount && rspApdu.p_data[0] > 0` **before** assigning the returned channel number, increasing `mOpenedchannelCount` and indexing `mOpenedChannels[resApduBuff.channelNumber]`. If the channel number is outside this admissible range, it sets the channel number to `-1` and the result to `ISecureElement::CHANNEL_NOT_AVAILABLE`. The baseline AOSP17 r1 code performed the array access without this specific check. This removes one class of out-of-range channel-index access when an SE response provides an unexpected channel number; it does **not** by itself establish full APDU response length validation, exploitability, a specific CVE, or correct behavior on every NFCC/SE.

**Vendor release nuance:** the pinned NXP 17.07.00 `snxxx/aidl/SecureElement.cpp` and `VirtualISO.cpp` also lack this specific channel bounds check. The newer-looking vendor release therefore **must not overwrite** the official r3 fix. The secure Android17 source direction here is the **official AOSP security revision** and a carefully controlled rebase, not importing archived 2023 or unguarded current vendor code.

An **experimental, nondefault, source-only** manifest `aosp17_pe_p2_se_security_candidate.xml` pins only `hardware/nxp/secure_element` to exact official commit `8aec22fde8121bf3f74006730ce42e9ac0366b62` under `android-security-17.0.0_r3`, preserving the existing project owner, groups and all other checkouts. It is explicitly **not** part of the 25 reviewed active stages or the active `default.xml`. A strict validator checks its exact three-node manifest shape, immutable SHA, source ownership and no other project changes; three adversarial tests reject a tampered SHA, switching `default.xml`, or redirecting `system/secure_element`.

**Before promotion:** compare the AIDL and HIDL fixes semantically against the actually selected build variant; validate NDK ABI/Soong, vendor NFC V1/V2 dependencies, OMAPI, VINTF, SELinux, response-length handling, CTS/VTS, signed firmware and physical mondrian. Coordinate security tags across the entire platform and NFC Mainline; **never set a newer SPL or claim full November patches merely because this isolated SE project was updated**.

## Nonnegotiable acceptance gates for mondrian

1. Determine actual NFC NFCC and eSE/UICC presence for the user's exact mondrian SKU/firmware. Match Xiaomi stock vendor SE HAL, VINTF, kernel `/dev` node, ELF `DT_NEEDED`, hardware service instances and SE/OMAPI permissions **before** selecting `android.hardware.secure_element-service.nxp`. Never infer `/dev/p73`, P73 or `SIM1/SIM2` from an unrelated repository.
2. Maintain **one** applicable system `android.hardware.secure_element.ISecureElement/eSE1` (or correctly vendor-confirmed instances) and one selected NFC `android.hardware.nfc.INfc/default`. Do not start both HIDL and AIDL SE services or duplicate vendor NXP extensions.
3. Validate frozen system SE AIDL V1 and NXP AIDL V1, NFC AIDL interface compatibility, native Soong links and vendor ABI. Check FCM/VINTF and SELinux enforcing/neverallow and Binder caller authorization for APDUs, SE controls, updates and OMAPI.
4. **No firmware/provisioning on audit**: never flash JCOP/LS/eSE firmware, modify bank/payment keys, force SPI reset or copy undocumented OMAPI certificate lists. Payment/HCE/eSE operation and certification are not established.
5. Once an independently developed PE-Reborn product is bootable, run NFC HAL + SE HAL VTS, OMAPI/ARA access-control tests, CTS, card/tag/HCE, eSE routing and recovery, suspend/resume, cold boot/OTA and power/latency measurements. Capture precise vendor/product logs and hardware identity.
6. LF52406 LineageOS 24.0 remains only an **exceptional, last-resort read-only hardware comparison** when needed. Do not import its device/product/policy architecture as the PE-Reborn implementation.
7. Security tags are **source revisions**, not claims that AOSP17 complete November 2026 SPL is integrated. Any security source candidate requires a coordinated whole-platform update.
